## Optional live demonstration narration

Use this only if you plan to run the simulator during the recording. A full run may take longer than the video, so it is reasonable to show a short smoke run or prepared artifacts.

1. In the Linux shell, show `cd /app/handover-simulator/src` and `python3 main.py --help`.
2. Say: “The workflow runs in Linux. Python source and inputs are bind-mounted from the project, while the ns-3 build and simulation execute in the container.”
3. To demonstrate a short run, use a small config and explicit DDQN limit, for example `python3 -u main.py --config /app/documentation/examples/quick.yaml --ddqnEpisodes 5 --ddqnTimeLimit 120`. Explain that runtime varies with container resources and ns-3 build state.
4. Show the timestamped run folder under `/app/handover-simulator/traces/` and the corresponding Windows folder `MAIN/handover-simulator/traces/`.
5. Open `run_status.json`; confirm `COMPLETE`, expected trace count, five result sets, and no errors before describing the run as complete.

## Claims to keep precise while recording

- Say “we integrated and extended this workflow” unless the team can identify authorship of a specific underlying algorithm or simulator component.
- Say “five handover result paths” because SBGH and ideal-SBGH are two variants in the same SBGH family.
- A `COMPLETE` status means expected files were produced and no algorithm error was recorded; it does not guarantee that every scientific metric is valid.
- The checked run results are single-run observations. Do not claim statistically significant superiority or DDQN convergence.
- Say “latency-related output” unless presenting a separately validated interruption-duration metric. Handover count alone is not a complete reliability measure.
- Do not say the algorithms prevent DoS or protect user privacy. Those controls are documented as future work.
